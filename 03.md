# 🧠 Part 3/10: Kernel & Core Engine (`nyx_core`)

> **Spec Purpose:** Authoritative kernel architecture. This module governs the client lifecycle, networking abstractions, player session caching, routing isolation, and the automated database migration layer.
> 
> **Performance Target:** Baseline idle CPU consumption $\le 0.003\text{ ms}$ on client; sub-millisecond memory lookups on server.
> 
>   

## 1. Database Schema & Migration Engine

### 1.1 Automated Migration Runner

Every resource must not rely on manual SQL file imports. `nyx_core` executes an automated bootstrap on `onResourceStart`.

  

- Reads directory: `nyx_core/sql/migrations/`
    
      
    
- Tracks executed state in dedicated table: `nyx_migrations`
    
      
    
- Execution must run in ordered sequence inside an isolated SQL transaction.
    
      
    

### 1.2 Base Table Schemas

SQL

```
-- Migration tracking table
CREATE TABLE IF NOT EXISTS `nyx_migrations` (
  `id` INT AUTO_INCREMENT PRIMARY KEY,
  `filename` VARCHAR(255) NOT NULL UNIQUE,
  `checksum` VARCHAR(64) NOT NULL,
  `executed_at` TIMESTAMP DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- Master player accounts (identifiers & global bans)
CREATE TABLE IF NOT EXISTS `nyx_accounts` (
  `account_id` INT AUTO_INCREMENT PRIMARY KEY,
  `license` VARCHAR(64) NOT NULL UNIQUE,
  `discord_id` VARCHAR(32) NULL,
  `steam_id` VARCHAR(32) NULL,
  `hwid_hash` VARCHAR(64) NOT NULL,
  `global_permissions` JSON DEFAULT ('["player"]'),
  `is_banned` TINYINT(1) DEFAULT 0,
  `ban_reason` TEXT NULL,
  `created_at` TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  `last_seen` TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  INDEX `idx_license` (`license`),
  INDEX `idx_hwid` (`hwid_hash`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- Character entities (per-player personas)
CREATE TABLE IF NOT EXISTS `nyx_characters` (
  `char_id` INT AUTO_INCREMENT PRIMARY KEY,
  `account_id` INT NOT NULL,
  `citizen_id` VARCHAR(16) NOT NULL UNIQUE,
  `first_name` VARCHAR(48) NOT NULL,
  `last_name` VARCHAR(48) NOT NULL,
  `dob` DATE NOT NULL,
  `gender` VARCHAR(16) NOT NULL,
  `wallets` JSON NOT NULL, -- {"cash": 500, "bank": 2500, "crypto": 0}
  `position` JSON NOT NULL, -- {"x": -1037.8, "y": -2737.9, "z": 20.1, "heading": 330.0}
  `metadata` JSON NOT NULL, -- {"health": 200, "armor": 0, "hunger": 100, "thirst": 100}
  `is_dead` TINYINT(1) DEFAULT 0,
  `deleted_at` TIMESTAMP NULL DEFAULT NULL,
  `created_at` TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (`account_id`) REFERENCES `nyx_accounts`(`account_id`) ON DELETE CASCADE,
  INDEX `idx_citizen_id` (`citizen_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- Audit ledger for critical transactions (anti-cheat & economy tracing)
CREATE TABLE IF NOT EXISTS `nyx_audit_log` (
  `log_id` BIGINT AUTO_INCREMENT PRIMARY KEY,
  `citizen_id` VARCHAR(16) NULL,
  `action` VARCHAR(64) NOT NULL,
  `payload` JSON NOT NULL,
  `ip_address` VARCHAR(45) NOT NULL,
  `timestamp` TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  INDEX `idx_char_action` (`citizen_id`, `action`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

## 2. Server Architecture: Memory Cache & State Engine

### 2.1 The Volatile Storage Layer (`Nyx.Players`)

Under no circumstance shall a script read or write to `oxmysql` during routine tick operations (e.g., getting cash, updating hunger, checking a job). All operational mutations run against the in-memory registry:

  

Lua

```
-- Conceptual server-side state registry
Nyx = Nyx or {}
Nyx.Players = {}         -- Keyed by source: [source] = PlayerObject
Nyx.CitizenLookup = {}   -- Keyed by citizen_id: [citizen_id] = source
Nyx.DirtyCharacters = {} -- Tracks modified records to debounce DB writes
```

### 2.2 Player Object Interface

Each connected and spawned player is encapsulated into a mutable class instance:

  

```
┌────────────────────────────────────────────────────────────────────────┐
│                              PlayerObject                              │
├────────────────────────────────────────────────────────────────────────┤
│ - source: number                                                       │
│ - accountId: number                                                    │
│ - charId: number                                                       │
│ - citizenId: string                                                    │
│ - data: { firstName, lastName, dob, gender }                           │
│ - wallets: Map<string, number> (cash, bank, crypto)                    │
│ - metadata: Map<string, any> (health, hunger, status effects)          │
│ - permissions: Set<string>                                             │
├────────────────────────────────────────────────────────────────────────┤
│ + getWallet(type): number                                              │
│ + addMoney(type, amount, reason): boolean                              │
│ + removeMoney(type, amount, reason): boolean                           │
│ + setMetadata(key, value): void                                        │
│ + getMetadata(key): any                                                │
│ + hasPermission(node): boolean                                         │
│ + save(): Promise<boolean>                                             │
└────────────────────────────────────────────────────────────────────────┘
```

### 2.3 Debounced Flush Strategy

- **Interval Sync:** A detached tick flushes dirty character data every `300` seconds using batched transactions.
    
      
    
- **Immediate Write Triggers:**
    
      
    - Character disconnect (`playerDropped`).
        
          
        
    - Character swapping / logout.
        
          
        
    - Large currency transfers exceeding dynamic audit limits.
        
          
        

## 3. High-Performance RPC & Callback Bus

Eliminates the legacy `TriggerServerEvent` / `RegisterNetEvent` back-and-forth boilerplate by implementing a native, promise-based RPC framework.

  

```
Client                                                         Server
  │                                                              │
  ├────── nyx:core:rpc:request (Nonce, Name, Args) ─────────────>│
  │                                                              │ [Handler Executed]
  │                                                              │ [Input Sanitized]
  │<───── nyx:core:rpc:response (Nonce, Status, Payload) ────────┤
  │                                                              │
[Promise Resolves]
```

### 3.1 Packet Wire Specifications

#### Request Packet (`nyx:core:rpc:request`)

|**Field**|**Type**|**Description**|
|---|---|---|
|`nonce`|`string`|Unique UUIDv4 generated on client per call|
|`route`|`string`|Namespace route (e.g., `characters:select`, `treasury:getBalance`)|
|`args`|`array`|Indexed array of parameters passed to handler|

#### Response Packet (`nyx:core:rpc:response`)

|**Field**|**Type**|**Description**|
|---|---|---|
|`nonce`|`string`|Matching request UUID|
|`success`|`boolean`|Execution outcome|
|`payload`|`any`|Returned data or `null`|
|`error`|`string \| null`|Standardized error code (e.g., `TIMEOUT`, `INVALID_AUTH`)|

### 3.2 Security Rules for the RPC Dispatcher

1. **Rate Limiting:** Enforce a token bucket per client (`source`). Maximum 50 RPC calls per second; exceeding kicks client for socket exhaustion attempts.
    
      
    
2. **Payload Size Limit:** Reject incoming client payloads $> 64\text{ KB}$ immediately.
    
      
    
3. **Execution Timeout:** Client automatically drops and rejects the promise if no response is returned within $5000\text{ ms}$.
    
      
    

## 4. Connection Pipeline & Virtual Routing Buckets

### 4.1 Deferrals Flow Chart

```
Incoming Connection
        │
        ▼
[Validate Identifiers] ──(Missing HWID or License)──> [Drop: Invalid Credentials]
        │
        ▼
[Check Ban Ledger] ──────(Hash Match Found)─────────> [Drop: Display Ban Card UI]
        │
        ▼
[Assign Routing Bucket] ──> Virtual Bucket ID = (1000 + Source)
        │
        ▼
[Handshake Client NUI]  ──> Deferral Complete ──> Spawn in Limbo Camera
```

### 4.2 Bucket & Entity Routing Rules

- While at the character select screen, the client is placed in **Virtual Bucket ID** ($1000 + \text{source}$).
    
      
    
- Client coordinates are frozen above the ocean or in an interior cell (`coords: 0.0, 0.0, -50.0`).
    
      
    
- No world entities (vehicles, peds, projectiles) can route to or from the client.
    
      
    
- When `characters:spawn` is validated server-side:
    
      
    1. Routing bucket resets to default (`0`).
        
          
        
    2. Coords and collision are loaded via client camera transition.
        
          
        
    3. Server applies cached health, armour, and appearance.
        
          
        
    4. Server emits global event `nyx:core:playerReady(source, citizenId)`.

## 6. Verification & Test Criteria

- [ ] **Resmon Benchmark:** Verify `nyx_core` stays strictly at $0.00\text{ ms}$ on client when standing still, and peaks at no more than $0.01\text{ ms}$ during spawn transitions.
    
      
    
- [ ] **Race-Condition Test:** Trigger 10 simultaneous money debit RPC calls from a modified client; verify server serializes mutations correctly and balance never drops below zero.
    
      
    
- [ ] **SQL Injection & Sanitization:** Verify all dynamic routes use prepared parameters; no concatenated SQL queries permitted anywhere in the pipeline.
    
      
    
- [ ] **Drop Persistence:** Force terminate the FiveM client process via `taskkill /F /IM FiveM.exe`; confirm server receives `playerDropped`, executes instant state-saving, and no dirty records are lost.
